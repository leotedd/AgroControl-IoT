# Matriz de compatibilidad MySQL → PostgreSQL

- **Fecha:** 2026-11-08 · Modo: sólo lectura
- **Alcance:** `database/schema.sql` (17 tablas, 2 triggers, 7 CHECK), `backend/src/**`, `backend/scripts/*.ts`, `database/importar-esquema.ps1`, `backend/scripts/pruebas-con-bd-temporal.mjs`.
- **Destino supuesto:** PostgreSQL 16/17 estándar (Supabase o Neon), sin extensiones propietarias salvo `citext` (opcional).
- **Leyenda:** 🟢 directo · 🟡 cambio mecánico · 🔴 cambio semántico o con riesgo

> No hay procedimientos almacenados, funciones, vistas ni eventos en el esquema. Los únicos objetos programados son los 2 triggers.

## 2. Tipos de datos y DDL

| Construcción MySQL | Dónde | PostgreSQL propuesto | Nivel | Nota |
|---|---|---|---|---|
| `INT UNSIGNED AUTO_INCREMENT` | 7 tablas | `INTEGER GENERATED BY DEFAULT AS IDENTITY` + `CHECK (id > 0)` implícito | 🟡 | `BY DEFAULT` permite cargar los ids originales en la migración; después hay que hacer `setval`. |
| `BIGINT UNSIGNED AUTO_INCREMENT` | 10 tablas | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | 🟡 | El contrato exige id ≤ 2^53−1. PostgreSQL lo cumple de sobra. |
| `INT/SMALLINT/TINYINT UNSIGNED` (no PK) | muchas columnas | Tipo con signo un escalón mayor (`SMALLINT UNSIGNED`→`INTEGER`, `INT UNSIGNED`→`BIGINT`) + `CHECK (col >= 0)` donde importe | 🟡 | `config_version_*` (INT UNSIGNED, hasta 4 294 967 295 según el contrato) → `BIGINT`. `uptime_ms BIGINT UNSIGNED` → `BIGINT` (2^63 es suficiente). |
| `TINYINT` usado como booleano (`activo`, `hora_estimada`, `confirmacion_tardia`, `reloj_confiable`…) | ~15 columnas | **Opción A:** `SMALLINT` + `CHECK (col IN (0,1))`: cero cambios en el código. **Opción B:** `BOOLEAN`: cambia literales `= 1` y parámetros `? 1 : 0` | 🟡 | **Recomendado: A** en la primera migración, para minimizar el riesgo. El código compara `activo = 1` y escribe `1/0`. |
| `ENUM(...)` | 16 columnas | `TEXT` + `CHECK (col IN (...))` | 🟡 | Se prefiere a `CREATE TYPE … AS ENUM` porque añadir valores es más simple y reversible. Ojo: un CHECK más por columna rompe el conteo de `verificacion.ts` (ver §5). |
| `DATETIME(3)` (UTC por convención) | todas las fechas | `TIMESTAMPTZ(3)` | 🔴 | En MySQL la convención UTC depende de `SET time_zone='+00:00'` en cada conexión. `TIMESTAMPTZ` es absoluto. El driver `pg` devuelve `Date`; verificar que `iso()` sigue produciendo `…Z` con milisegundos. Los parámetros `Date` se envían con zona. |
| `DEFAULT CURRENT_TIMESTAMP(3)` | todas | `DEFAULT now()` (o `clock_timestamp()`) | 🟡 | `now()` es la hora de **inicio de la transacción**, mientras que en MySQL `NOW(3)` es por sentencia. Afecta poco (transacciones cortas). Usar `clock_timestamp()` si se requiere el instante exacto. |
| `ON UPDATE CURRENT_TIMESTAMP(3)` | 10 tablas | Trigger genérico `BEFORE UPDATE … SET NEW.actualizado_en = now()` | 🔴 | **Añade 10 triggers.** El de `ordenes_riego` no aplica (no tiene `actualizado_en`). Cambia el conteo de triggers de `verificacion.ts`. |
| `DECIMAL(p,s)` | humedad, coordenadas, áreas | `NUMERIC(p,s)` | 🟡 | `pg` devuelve NUMERIC como **string**. mysql2 usa `decimalNumbers:true` (número). Hace falta `types.setTypeParser(1700, parseFloat)` o conversión explícita. |
| `BIGINT` devuelto | ids de órdenes, mediciones… | `pg` devuelve int8 como **string** | 🔴 | mysql2 con `supportBigNumbers` devuelve número si es seguro. El código hace `Number(o.id)` en algunos sitios, pero no en todos (p. ej. `vistas.has(o.actuador_id)` y comparaciones `===`). **Fijar `setTypeParser(20, BigInt→Number con chequeo ≤ 2^53−1)`**. |
| `COUNT(*)` | muchas | Devuelve `bigint` (string en `pg`) | 🟡 | Ya se envuelve en `Number(...)` en la mayoría de los casos; el parser global (20) lo resuelve. |
| `JSON` | 6 columnas | `JSONB` | 🔴 | `JSONB` normaliza el orden de claves y elimina duplicados. `ack_cuerpo` deja de ser byte a byte el cuerpo recibido. La igualdad del trigger (`OLD.parametros <=> NEW.parametros`) pasa a ser semántica, lo cual es correcto. `pg` devuelve el objeto ya parseado; el código tolera ambos (`typeof === 'string' ? JSON.parse : …`). Si se necesita fidelidad literal, usar `JSON` (texto). |
| `TEXT`, `VARCHAR(n)`, `CHAR(n)` | — | Iguales | 🟢 | `CHAR(n)` rellena con espacios en PostgreSQL. Todos los `CHAR` de este esquema tienen longitud fija real (hash 64, uuid 36, arranque 8): sin impacto. |
| `utf8mb4_0900_ai_ci` (insensible a mayúsculas y acentos) | todas | Sensible por defecto | 🔴 | **`usuarios.email` UNIQUE**: en MySQL `A@x.com` = `a@x.com`. El login hace `toLowerCase()`, pero el seed y futuros altas no garantizan minúsculas. Usar `UNIQUE (lower(email))` o `CITEXT`. Resto de comparaciones: códigos en mayúsculas validados por regex, sin impacto. |
| `UNIQUE` con NULL (`token_hash`, `token_anterior_hash`, `(solicitada_por, idempotency_key)`) | dispositivos, ordenes | Igual: NULL no colisiona | 🟢 | Mismo comportamiento. |
| `ENGINE=InnoDB DEFAULT CHARSET…` | todas | Eliminar | 🟢 | |
| `KEY ix_…` en línea | todas | `CREATE INDEX` separado | 🟡 | Los nombres de índice son globales por esquema en PostgreSQL: los actuales ya son únicos. |
| FK `ON DELETE CASCADE/SET NULL/RESTRICT` | 30+ | Iguales | 🔴 | Ver §3.3: **en PostgreSQL las acciones FK sí disparan triggers.** |

## 3. Restricciones y triggers

### 3.1 CHECK (7)

| CHECK | Traducción | Nivel |
|---|---|---|
| `ck_dispositivos_intervalos` | Idéntica (`BETWEEN`) | 🟢 |
| `ck_dispositivos_tope` | Idéntica | 🟢 |
| `ck_sensores_calibracion` | `ABS(raw_seco - raw_humedo) >= 200` (columnas `INTEGER`; sin `CAST AS SIGNED`) | 🟡 |
| `ck_cc_histeresis` | Idéntica (NUMERIC) | 🟢 |
| `ck_cc_rangos` | Idéntica | 🟢 |
| `ck_ordenes_ttl` | Idéntica | 🟢 |
| `ck_ordenes_duracion` | Idéntica | 🟢 |

Además, el comentario del esquema señala que «MySQL no admite CHECK sobre AUTO_INCREMENT». PostgreSQL sí: se puede añadir `CHECK (id <= 9007199254740991)` en `ordenes_riego`, pero **cambia el conteo** de CHECK.

### 3.2 Triggers (2)

| Elemento MySQL | PostgreSQL | Nivel |
|---|---|---|
| `DELIMITER $$ … CREATE TRIGGER … BEGIN … END$$` | `CREATE FUNCTION trg_x() RETURNS trigger LANGUAGE plpgsql AS $$ … $$;` + `CREATE TRIGGER … FOR EACH ROW EXECUTE FUNCTION trg_x();` | 🟡 |
| `a <=> b` (igualdad NULL-segura) | `a IS NOT DISTINCT FROM b` | 🟡 |
| `SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT='…'` | `RAISE EXCEPTION '…' USING ERRCODE = 'P0001'` (o un código propio) | 🟡 |
| `OLD.parametros <=> NEW.parametros` (JSON) | `OLD.parametros IS NOT DISTINCT FROM NEW.parametros` (con `JSONB` es igualdad semántica; con `JSON` **no existe el operador `=`**, hay que comparar `::text`) | 🔴 |
| BEFORE DELETE que siempre falla | `RAISE EXCEPTION` en una función `BEFORE DELETE` | 🟡 |

### 3.3 Diferencia semántica crítica: FK y triggers

El esquema MySQL documenta que *«las acciones de claves foráneas (ON DELETE SET NULL / CASCADE) no activan triggers en MySQL: la retirada administrativa de un dispositivo o usuario sigue siendo posible»*.

**En PostgreSQL ocurre lo contrario:** las acciones referenciales se ejecutan como UPDATE/DELETE internos que **sí disparan** los triggers de fila del usuario. Consecuencias:

| Acción | MySQL | PostgreSQL sin ajuste |
|---|---|---|
| `DELETE FROM usuarios WHERE id=…` con órdenes suyas (`solicitada_por` ON DELETE SET NULL) | Permitido | **Falla**: `trg_ordenes_inmutables` (a) prohíbe cambiar `solicitada_por` |
| `DELETE FROM dispositivos …` (CASCADE a `ordenes_riego`) | Permitido | **Falla**: `trg_ordenes_sin_borrado` |
| Borrar una orden que reemplazó a otra (`cerrada_por_orden_id` SET NULL) | Imposible igualmente | Igual |

**Opciones** (decisión de diseño, ver PLAN_MIGRACION §Decisiones):
1. Comprobar `pg_trigger_depth() > 1` en el trigger para permitir cambios originados por cascadas. Es frágil.
2. Permitir en (a) la transición `solicitada_por/cancelada_por → NULL` y en el trigger de borrado consultar si el dispositivo padre está siendo eliminado. Más complejo.
3. **Recomendado:** aceptar el comportamiento más estricto de PostgreSQL. La retirada de dispositivos y usuarios se hace por baja lógica (`estado='DESHABILITADO'`, `activo=0`), que el código ya usa. Documentarlo y probar que ninguna ruta borra usuarios o dispositivos (verificado: ninguna lo hace).

## 6. Alternativa: conservar MySQL en un motor «compatible» (TiDB Cloud Starter)

| Aspecto | Estado en TiDB | Impacto |
|---|---|---|
| Triggers | **No admitidos** (TiDB no implementa triggers, procedimientos ni eventos; reconfirmar en la página *Limited SQL Features*) | Se pierde la defensa en BD de la inmutabilidad. Las guardas `WHERE … AND resultado IS NULL` del código la mantienen sólo a nivel de aplicación. **El arranque falla** (`verificacion.ts` exige los triggers). |
| CHECK | Se aplican sólo con `tidb_enable_check_constraint=ON` (desactivado por defecto) | Verificar si Starter permite activarlo |
| `AUTO_INCREMENT` | Único, pero **no monótono entre nodos** salvo `AUTO_ID_CACHE=1` | Rompe la regla del contrato §8.2 (ids crecientes por dispositivo en orden de entrega) si no se configura |
| `SELECT … FOR UPDATE` | Modo pesimista, compatible | 🟢 |
| `INSERT IGNORE`, `IF()`, `INTERVAL`, JSON | Compatibles | 🟢 |
| Colación `utf8mb4_0900_ai_ci` | Admitida en versiones recientes (verificar) | 🟡 |
| Cuota | 50 M RU/mes por instancia, 5 GiB de filas; al agotarse se **rechazan conexiones** hasta el mes siguiente | Con ≈ 11 M sentencias/mes es probable que quepa, pero no está medido |

Conclusión: TiDB reduce el trabajo de código (≈ 1–2 días), pero **degrada garantías de seguridad del contrato** y no es MySQL real. Es inferior a PostgreSQL (que conserva triggers y CHECK) y a MySQL en una VM *Always Free* (que lo conserva todo).
